## Abstract

Recent advances have extended the context window of frontier LLMs dramatically, from a few thousand tokens up to millions. However, the compute costs of inferencing long-context LLMs are massive and often prohibitive in practice. RAG offers an efficient and effective alternative: retrieve and process only the subset of the context most important for the current task. Although promising, recent work applying RAG to long-context tasks has two core limitations: 1) there has been little focus on making the RAG pipeline compute efficient, and 2) such works only test on simple QA tasks. To address this, we develop an algorithm based on PageRank which we call mixture-of-PageRanks (MixPR). MixPR uses a mixture of PageRank-based graph-retrieval algorithms implemented using sparse matrices for efficient, cheap retrieval. Our MixPR retriever achieves state-of-the-art results across a wide range of long-context benchmark tasks, outperforming both existing RAG methods, specialized retrieval architectures, and long-context LLMs despite being far more compute efficient. Due to using sparse embeddings, our retriever is extremely compute efficient, capable of embedding and retrieving millions of tokens within a few seconds and runs entirely on CPU.

## Problem Statement

Long-context RAG operates in a different regime from ordinary RAG. In ordinary RAG the corpus is embedded **once, before deployment**; in long-context tasks a fresh document arrives at test time, so **chunking and embedding happen inside the query's latency budget**. A transformer embedder that is acceptable as a one-off indexing cost becomes prohibitive when it must run per query.

The paper attacks two problems at once:

1. **The retrieval problem** — nearest-neighbour search works for single-step lookup but fails when relevant chunks are linked only *indirectly* to the query (multi-hop), or when the task needs globally important content rather than query-similar content (summarization).
2. **The compute problem** — the retriever's own cost is rarely measured and is often the bottleneck.

## Key Contributions

1. **MixPR** — a PPR-based retrieval algorithm that **dynamically switches the teleport parameter α by task type**, handling local (query-dependent) and global (query-independent) retrieval with one algorithm.
2. **A graph-construction method requiring no LLM and no neural network**: the adjacency matrix is the chunk–chunk TF-IDF proximity matrix.
3. **Evaluation across 22 tasks** in four long-context benchmarks (14 single-hop, 8 multi-hop, 3 global), with SOTA or near-SOTA on three.
4. **Demonstrated real-time CPU operation** — millions of tokens chunked, embedded and retrieved in seconds on a desktop.

## Methodology / Architecture

### PageRank and Personalized PageRank

Plain PageRank is the steady state of the Markov chain `π = Aπ`, capturing pure structural importance. Personalized PageRank biases it toward a personalization distribution *p*:

```
π = (1 − α) A π + α p
```

**Note the convention**: here **α is the teleport weight**, so α → 1 makes retrieval purely query-dependent and α → 0 reduces to plain PageRank (purely structural). This is the same convention as SPRIG's `r = αs + (1−α)Pᵀr`, but the operating points are very different — SPRIG uses α = 0.15, MixPR uses α = 0.6.

### Chunking

Sentence-first, then split on newlines, then on word boundaries, until every chunk is under **N = 32 words**. Used unchanged across all experiments.

### Graph construction — the cheap part

Each chunk is embedded, L2-normalized, and stored in chronological order as columns of *E*. The adjacency matrix is simply:

```
A = normalize(Eᵀ E)
```

i.e. the **chunk–chunk cosine proximity matrix**, column-normalized. No LLM, no triples, no entities.

> **This is architecturally different from SPRIG, LinearRAG and HippoRAG**, which all build *entity–document bipartite* graphs. MixPR's graph is chunk–chunk. SPRIG's "TF-IDF Graph PPR (MixPR-like)" baseline reproduces the *sparse-embedding* aspect but on a term graph, which is why SPRIG's own graph statistics (Table A.4) show its term graph with p95 entity degree 298 versus 5 for its entity graph.

### Personalization vector — the unusual part

Chunks are stored chronologically, and in the benchmarks used **the query is the last sentence or two of the input**. So *p* is a one-hot vector on the final chunk (or 0.5/0.5 on the last two). The query is literally a node in the graph, and PPR random-walks outward from it.

This is elegant for the long-context setting and **does not transfer to a standing corpus**, where the query is not part of the indexed text. CTRA, SPRIG and HippoRAG all need an explicit seeding step instead — which is exactly what `GraphHybrid`/`GraphDense`/`GraphRRF` are.

### Dynamic α — the "mixture"

The authors swept α on local vs global tasks (Figure 3):

- **Local (QA, needle-in-a-haystack)**: α between 0.5 and 0.99 gives high recall; 0.1 ≤ α ≤ 0.5 slightly worse; **α = 0 fails completely**.
- **Global (summarization, word-frequency extraction)**: smaller α better, **α = 0 best**.

This motivates a two-expert router: PPR with α > 0.5 for local, plain PR (α = 0) for global. The router is an LLM zero-shot prompt over the first two and last two sentences of the context, answering 'y'/'n'. Reported to work "nearly perfectly." Production α = 0.6 for local tasks throughout.

### Sparse implementation

TF-IDF via scikit-learn, stored in SciPy sparse matrices; PPR is sparse matrix–vector multiplication. Entirely CPU. "The fact that our retrieval method runs solely on CPU means that it can run in tandem with an LLM running on the GPU."

## Datasets

| Benchmark | Content |
|---|---|
| **BABILong** | 5 bAbI question types with PG-19 book text as filler, 0k–10M tokens |
| **RULER** | 13 tasks: NIAH variants, 2 QA, 2 agglomerative (cwe/fwe), 1 variable tracing |
| **Hash-Hop** | Variable tracing over hash assignments, 1–6 hops, 100k–500M tokens |
| **InfiniteBench Eng.Sum** | Book summarization, ~80k–800k tokens |

22 tasks total: 14 single-hop local, 8 multi-hop, 3 global.

## Results

### BABILong (Table 1, average over 0k–10M)

| Model | Avg |
|---|---|
| ARMT (fine-tuned) | 94.8 (1st) |
| **GPT-4o + MixPR-RAG** | **80.4 (2nd)** |
| RMT-Retrieval (fine-tuned) | 71.0 (3rd) |
| RMT (fine-tuned) | 69.0 (4th) |
| **GPT-4o-mini + MixPR-RAG** | **66.0 (5th)** |
| GPT-4o (no RAG) | 48.3 |
| GPT-4o-mini (no RAG) | 41.3 |
| Llama3-ChatQA-1.5-8B + RAG | 43.3 |

GPT-4o goes 48.3 → 80.4 with MixPR. The three models above it are **fine-tuned specifically for BABILong**; MixPR is not.

### RULER (Table 2, average over 4k–128k)

| Model | Avg |
|---|---|
| **GPT-4o + MixPR-RAG** | **96.5 (1st)** |
| Jamba-1.5-large | 96.0 (2nd) |
| Gemini-1.5-pro | 95.8 (3rd) |
| GPT-4o | 95.3 (4th) |
| **GPT-4o-mini + MixPR-RAG** | **94.9 (5th)** |
| GPT-4o-mini | 92.3 |

Gains concentrate at long context: GPT-4o-mini at 128k goes 85.4 → 93.6.

### Hash-Hop (Table 3)

GPT-4o-mini + MixPR holds 96–97 from 100k to **500M tokens**, essentially flat, and beats the fine-tuned LTM-Magic.dev model at 100M (96 vs 90).

### Multi-hop specifically (Figure 4)

MixPR improves over non-graph RAG baselines "by as much as 50%" on BABILong types 2–3 and Hash-Hop, while baseline RAG degrades quickly with input length.

**An important negative result, volunteered by the authors**: on RULER's variable-tracing task the plain hybrid retriever also does well, because each assignment is labelled `VAR`, which is semantically close to "variable" in the query — so a single similarity comparison shortcuts the multi-hop structure. They conclude "this test is a weak test of multi-hop retrieval."

### Compute (Figure 6; AMD Threadripper PRO 5955WX 16-core + RTX 4090)

Sparse models chunk, embed and retrieve **1.5M+ tokens in a few seconds**; dense embedders (500M and 33M BERT) take **several minutes** for the same input, on GPU. The bottleneck is embedding, not retrieval: "the program that computes TF-IDF embeddings runs with extremely low latency on the CPU."

## Limitations

- **The evaluation regime is long-context, not corpus retrieval.** Every result assumes the document arrives at query time and the query is the last chunk. The headline numbers do not directly transfer to a standing index.
- **The α router depends on an LLM call** — cheap relative to the task, but it is a neural component in a pipeline advertised as using "no neural networks for graph-construction or embedding."
- **Two-point α mixture only.** The router picks α ∈ {0, 0.6}; no continuous adaptation, and the routing accuracy is reported qualitatively ("nearly perfectly," figure 11) rather than as a confusion matrix.
- **TF-IDF inherits lexical brittleness.** Synonyms, abbreviations and morphological variants are not matched. The benchmarks (bAbI, hash tracing, NIAH) are unusually friendly to exact lexical matching.
- **Summarization evaluation is weak, and the authors say so**: ROUGE-L scores are "similar across RAG models," gains appear only under BertF1, and "summarization quality is notoriously difficult to assess."
- **A = normalize(EᵀE) is dense in principle.** For *n* chunks this is *n*×*n*; feasible at long-context scale (thousands of chunks) but the paper does not report how it is thresholded or sparsified at corpus scale.
- **Single-run measurements** for the compute curves.

## Relevance to CTRA

1. **It is the strongest existence proof that PPR retrieval need not be expensive.** CTRA's LinearRAG implementation has three measured walls (`research/rag-alternatives-hybrid-retrieval.md`): a GPU wall at indexing (**GLiNER at 1.13 doc/s → 22.8 days for ClinicalTrials.gov alone**), a RAM wall (13–100 GB in-RAM embedding store vs 7 GB available), and a query-time CPU wall. MixPR shows the PPR *itself* is not the problem — sparse matrices and SciPy handle millions of tokens in seconds on CPU. **The cost in CTRA is entirely in the entity-extraction and embedding layers, not the graph traversal.**

2. **It is the cheapest possible graph, and therefore the right ablation floor.** `A = normalize(EᵀE)` over TF-IDF vectors requires no NER at all — no GLiNER, no spaCy, no gazetteer. Before CTRA spends anything further on entity extraction, this is the baseline that establishes how much of the graph's value comes from entities versus from mere lexical co-occurrence. SPRIG measured its analogue and found it weak (TF-IDF Graph R@10 0.419 HotpotQA / 0.375 2Wiki, **below plain BM25**) — but SPRIG's variant is a *term* graph, not MixPR's *chunk* graph, so that is suggestive rather than decisive.

3. **The α finding is directly reusable, with a caveat.** MixPR measured α = 0 failing completely on query-dependent tasks and winning on global ones. CTRA's retrieval is entirely query-dependent (feature-engineering agents asking about a specific trial), so this argues for **high teleport weight** — closer to MixPR's 0.6 than to SPRIG's 0.15 or HippoRAG's 0.5. Worth noting the three papers disagree substantially on this parameter, which is itself evidence it needs local measurement.

4. **The personalization trick does not transfer, and that gap is the whole point of the seeded variants.** MixPR gets its seed for free because the query is the last chunk of the input. CTRA queries a standing index, so it must seed explicitly — which is precisely what `GraphHybrid` / `GraphDense` / `GraphRRF` do, and why those variants exist.

5. **"Sparse retrieval runs on CPU alongside an LLM on the GPU"** is the deployment shape CTRA needs: the GTX 1650 Ti's 4 GB is better spent on the generation/agent side than on retrieval.
