## Abstract

GraphRAG systems improve multi-hop retrieval by modeling structure, but many approaches rely on expensive LLM-based graph construction and GPU-heavy inference. The paper presents **SPRIG**, a CPU-only, linear-time, token-free GraphRAG pipeline that replaces LLM graph building with lightweight NER-driven co-occurrence graphs and uses Personalized PageRank (PPR) for retrieval. It is evaluated on HotpotQA and 2WikiMultiHopQA against BM25, dense retrieval, reciprocal-rank fusion (RRF), and a TF–IDF PPR baseline, focusing on retrieval quality and system efficiency. The paper provides ablations over seed size, NER choice, and PPR parameters, plus scalability curves and end-to-end QA on a 1,000-query subset. Lightweight alias disambiguation and hub pruning reduce query time by 16–28% with negligible Recall@10 changes. The results characterize when CPU-friendly graph retrieval helps multi-hop recall and **when strong lexical hybrids (RRF) are sufficient**, outlining a path to democratizing GraphRAG without token costs or GPU requirements.

## Problem Statement

Graph-based retrieval augments RAG with structured traversal, but most GraphRAG variants rely on LLMs for relation extraction or graph summarization, driving up cost and hardware requirements. This blocks adoption in academic and low-resource settings where CPU-only constraints and tight memory budgets are common.

The paper studies one pragmatic question: **how far can you get with a linear-time, CPU-only GraphRAG that uses no LLMs during indexing?** The stated significance is twofold — it addresses a real deployment bottleneck (teams that cannot afford LLM-based graph construction at scale or GPU-based graph inference), and it provides a fully reproducible CPU-only baseline with explicit complexity and memory reporting as a reference point for efficient/green RAG work.

Deliberately, the evaluation is **retrieval-only** rather than end-to-end generation, in order to isolate indexing and traversal effects.

## Key Contributions

1. **SPRIG** — a CPU-only, linear-time, token-free GraphRAG pipeline built on NER-based entity–document co-occurrence graphs.
2. **Three lightweight refinements for CPU settings**: (i) title-alias entity disambiguation (**SPRIG-EL**), (ii) hub pruning / edge caps (**SPRIG-PRUNE**), and (iii) explicit entity–document seed mixing (**SPRIG-MIX**).
3. **GraphHybrid / GraphDense variants** that improve Recall@10 over BM25 on both datasets via hub-aware normalization and rank-weighted seeding.
4. **Comparisons against CPU-friendly baselines** (RM3 pseudo-relevance feedback, BM25 + cross-encoder reranking) plus an ANN-vs-exact seeding analysis.
5. **Extensive efficiency reporting** — scalability curves, per-query latency distributions, peak RSS under a 4 GB cap, and ablations over seed size, seed weighting, hub penalty and PPR mode.

## Methodology / Architecture

### Pipeline Overview

A deterministic six-step sequence:

1. Normalize text
2. Extract entities with lightweight NER
3. Build an entity–document bipartite graph with TF–IDF weighting
4. Create a seed distribution from the query (entities, or top-*k* BM25/dense passages) with optional rank-based weighting
5. Run PPR by power iteration or a push-based approximation
6. Rank passages by PPR scores

Indexing stays linear in corpus size; inference is bounded by sparse matrix–vector multiplications.

### Graph Construction (Linear-Time)

An **entity–document bipartite graph**. For each passage *d*, entities *e* are extracted with lightweight NER — either spaCy or a **regex heuristic** matching 1–4 token capitalized spans:

```
\b[A-Z][a-z]+(\s+[A-Z][a-z]+){0,3}\b
```

Optional entity normalization (lowercasing, stripping non-alphanumerics) reduces surface-form variation. Edges are weighted by TF–IDF:

> w(e,d) = tf(e,d) · log( (N + 1) / (df(e) + 1) ) + 1

where *N* is the passage count and *df(e)* the entity document frequency. The adjacency matrix **W** is row-normalized to the transition matrix **P = D⁻¹W** (row-stochastic). The process is linear in the number of entity mentions and invokes no LLM.

A **TF–IDF term–document graph** (a MixPR-like baseline) is built by replacing entities with tokens, filtering terms with *df* < 3 or *df* > 0.1·N.

**No full entity linking or coreference resolution is performed.** Instead:

- **SPRIG-EL**: a lightweight title-alias map from normalized mentions to unambiguous document-title aliases (e.g. stripping parenthetical disambiguators) — zero-KB, CPU-only, no external supervision.
- **Hub downweighting**: document→entity edges scaled by *df(e)⁻ᵖ* (p ≥ 0) to reduce the influence of high-degree entity hubs.
- **SPRIG-PRUNE**: optionally remove the top-*x*% entities by *df* and/or cap per-entity outdegree to the top-*L* TF–IDF edges, reducing |E| and PPR cost.

### Retrieval via PPR

Given a query, either query entities are identified (**Graph** variant) or BM25/dense retrieval selects seed passages (**GraphHybrid** / **GraphDense**). PPR runs with damping *α* for *T* iterations (power iteration) or via a push-based approximation with residual threshold *ε*:

> r = α·s + (1 − α)·Pᵀr

where **s** is the seed distribution over entity/passage nodes and **P** is the row-stochastic transition matrix over the combined entity + document node set. The standard PPR update with **Pᵀ** is used — explicitly *not* a two-step (P²) variant. On a bipartite graph the walk naturally alternates between entities and documents; passages are ranked by the document slice of **r**.

### Seed Mixing (SPRIG-MIX)

For the hybrid variants, separate seed vectors **sₑ** (entities) and **s_d** (seed passages) are mixed:

> s = norm( α_mix·sₑ + (1 − α_mix)·s_d )

with L1 normalization over nonzero entries. Default is *mass-proportional* mixing; an adaptive option uses α_mix = (nₑ + 1) / (nₑ + n_d + 2) with Laplace smoothing. If either partition is empty, the pipeline falls back to the other. Seed mass on the top-*k* BM25/dense passages uses raw, softmax, or **rank-based weighting** (rank weighting in main results). Queries yielding no recognized entities fall back to a uniform distribution over passages; a BM25 top-1 fallback is evaluated in the appendix.

### Complexity and Memory

- Graph construction: **O(M)** where *M* is the number of entity (or term) mentions; |E| scales with mentions.
- Each PPR query: **O(T · E)** via sparse matrix–vector multiplication.
- Memory: **O(E + V)** for sparse adjacency and node scores.
- Push-based PPR replaces fixed iterations with residual-driven updates, reducing work on sparse queries.
- Hub pruning / edge caps reduce |E| directly, lowering query time while preserving most recall.

Peak RSS plus index/query RSS are reported to verify the 4 GB constraint. Appendix Table A.4 shows entity graphs have heavy-tailed degree distributions, motivating the degree-aware normalization.

## Datasets

| Dataset | Split | Queries | Passages |
|---|---|---|---|
| HotpotQA | validation | 7,405 | 66,581 |
| 2WikiMultiHopQA | validation | 10,000 | 45,902 |

Dataset-provided passages are used as retrieval units **without additional chunking**, to keep preprocessing deterministic and reflect the standard multi-hop QA setting.

## Experimental Setup

**Baselines (10):** BM25 · BM25+RM3 · BM25-2step (entity query expansion) · Dense (BAAI/bge-small-en-v1.5) · RRF (BM25+dense, k=60) · BM25+CE (TinyBERT cross-encoder on top-100) · TF–IDF Graph PPR (MixPR-like) · Graph (query-entity seeded) · GraphHybrid (BM25 seeds) · GraphDense (dense seeds).

**Metrics:** Recall@K, Hit@K, MRR. The paper notes MRR "can be high even when Recall@K is moderate under multi-label ground truth" — it only uses the rank of the *first* relevant passage. End-to-end QA measured with DistilBERT extractive QA on 1,000-query subsets.

**Environment:** CPU-only under a **strict 4 GB RAM budget**. spaCy `en_core_web_sm` v3.8.0 (spaCy 3.8.11). Graph construction costs **~9–10 ms/doc with spaCy** vs **~0.02 ms/doc with the regex heuristic**. Dense retrieval uses HNSW with M=32, efConstruction=200, efSearch=64.

**PPR settings:** α = 0.15, max_iter = 5; push-based PPR for HotpotQA, power iteration for 2Wiki. min_entity_len = 2, min_entity_df = 1, max_entity_df_ratio = 1.0. Seed sizes k=5 (GraphDense) / k=10 (GraphHybrid) for HotpotQA; k=3 / k=5 for 2Wiki. Rank-based seed weighting, hub downweighting p = 0.5, seed-entity downweighting q = 0.5 (HotpotQA) / 1.0 (2Wiki).

**Tuning protocol:** hyperparameters tuned on a 500-query subset of each validation set; main tables computed on full validation splits. The paper acknowledges this may introduce mild validation overfitting and reports a robustness check removing the tuning subset (Appendix Table A.15), plus paired bootstrap confidence intervals (A.18–A.21).

**QTime** is end-to-end per-query time *including* the seeding stage for externally-seeded graph variants.

### Effect of lightweight enhancements (Table 4, GraphHybrid, full validation)

| Variant | Hotpot R@10 | Hotpot QTime | 2Wiki R@10 | 2Wiki QTime |
|---|---|---|---|---|
| Base | 0.775 | 485.3 s | 0.743 | 367.9 s |
| +ALL (EL + PRUNE + MIX) | 0.773 | **350.5 s** | 0.743 | **308.5 s** |

Hub pruning (top 1% entities by *df*) and explicit seed mixing cut query time **~16–28%** with negligible recall change. Appendix Table A.10 shows pruned entities rarely overlap gold-title mentions — pruning removes generic hubs, not rare bridge entities.

### ANN vs exact seeding (Table 3)

Tuned HNSW produced **identical** full-validation GraphDense numbers to the defaults on both datasets (HotpotQA R@10 0.844; 2Wiki 0.747). ANN sensitivity appears on 2k-query subsets (A.11–A.12) but washes out at full scale.

### Efficiency and scalability

Indexing scales roughly linearly with corpus size. Query time grows with graph density and PPR iteration count. Externally-seeded graph variants (GraphHybrid/GraphRRF) are the most expensive graph methods; **the cross-encoder reranker is the most expensive overall**. Non-monotonic fluctuations in dense index time are attributed to HNSW randomness, caching/IO and OS scheduling (each size run once).

### Other findings

- **The TF–IDF term graph performs poorly** relative to entity graphs (R@10 0.419 / 0.367), supporting lightweight NER over term-level edges even without full entity linking.
- **RM3 underperforms plain BM25** on both datasets — classic pseudo-relevance feedback is not reliable for multi-hop retrieval.
- **Rank-based seeding beats raw or softmax weighting**; modest hub downweighting (p ≈ 0.5) improves robustness.
- **Regex NER is orders of magnitude faster** than spaCy for indexing and "can be competitive for Graph-only retrieval"; spaCy is retained in main tables as a standard baseline.
- **Graph-only retrieval is most sensitive to missed entities**; GraphHybrid is more robust because BM25 seeding compensates for NER errors (A.9).
- **End-to-end QA gains are modest** — retrieval improvements do not translate proportionally into downstream EM/F1 under a small extractive reader (A.14).

## Limitations

Stated by the author:

1. **Scope** — retrieval evaluated on only two multi-hop QA datasets; end-to-end QA only on 1,000-query subsets with a small extractive model.
2. **No full entity linking or coreference resolution** — title-alias disambiguation is intentionally minimal and resolves only unambiguous aliases, so high-degree entities and residual ambiguity still introduce noise.
3. **NER quality is proxied, not measured** — sensitivity is estimated via query-entity coverage and gold-title matches; no human-labeled NER precision/recall.
4. **ANN trades recall for speed** — default HNSW settings can underperform exact seeding.
5. **One dense encoder in main results** — stronger encoders or cross-encoders may shift the accuracy–latency frontier.
6. **Hyperparameters tuned on validation subsets** rather than a held-out split, risking mild overfitting.
7. **No head-to-head runs against LinearRAG, HippoRAG or TERAG** — positioning against token-efficient GraphRAG pipelines is conceptual only. Likewise LADR and MoPo are positioned qualitatively (A.17), not re-implemented.

Additional observations not flagged by the author:

8. **Query-time cost remains high** — the paper concedes graph traversal "requires further optimization for latency-sensitive applications." Dense-only retrieval is 6–8x faster than every graph variant.
9. **Wikipedia-domain only** — both datasets are Wikipedia multi-hop QA with gold supporting-passage labels. Entity distribution, NER difficulty and vocabulary variance differ sharply from specialised domains.

## Relevance to CTRA

This is the closest published work to the CTRA RAG-backend decision analysed in `research/rag-alternatives-hybrid-retrieval.md`. It benchmarks precisely the alternatives CTRA is choosing between, CPU-only, under a 4 GB budget — comparable to CTRA's development hardware (see `notes/bench_rag_hardware/`).

1. **Pure entity-graph PPR is weak on its own.** Query-entity-seeded `Graph` scores R@10 of **0.464 / 0.357** — *well below plain BM25* (0.742 / 0.643). This is the closest published analogue to LinearRAG's retrieval mechanism (entity activation → PPR), and it indicates the graph is not a standalone retriever. It becomes competitive only when seeded from dense or lexical retrieval. That is a caution about the mechanism CTRA currently depends on, independent of its cost.

2. **GraphRRF validates the hybrid-first sequencing.** The best Recall@10 on both datasets comes from PPR seeded by the fused BM25+dense list. If CTRA later shows a genuine multi-hop deficit, the fix is PPR on top of hybrid retrieval — which makes the hybrid retriever a **prerequisite** for the good version of the graph, not an alternative to it.

3. **The cross-encoder buys precision, not recall.** RRF+CE gives the best MRR in the study (0.887 on HotpotQA) while *slightly lowering* R@10 versus RRF alone (0.846 vs 0.851). It is also the most expensive method overall. For CTRA — where the feature-builder agent reads top chunks and extracts a value — top-of-list ordering is the right thing to buy, but it should be an explicit choice, and the CE belongs on top of **RRF**, not BM25 alone.

4. **The cost gap is the NER model, confirming CTRA's measurements.** SPRIG's graph construction runs at **9–10 ms/doc** with `en_core_web_sm` (0.02 ms/doc with regex). CTRA measured GLiNER-BioMed-large at **~860 ms/chunk** on a GTX 1650 Ti — roughly 100x. A CTRA graph built with small-model NER would index ClinicalTrials.gov in hours, not the measured 22 days.

5. **Hub pruning is a free CPU-time lever.** Removing the top 1% of entities by document frequency cut query time 16–28% with no recall loss, and pruned entities rarely overlap gold mentions. Biomedical corpora have severe hub problems (`patients`, `treatment`, `study`, `safety`), so this likely transfers well.

6. **Rank-based seeding and hub downweighting** (p ≈ 0.5, entity downweight by *df⁻ᑫ*) are cheap, portable wins. Note that `schemagraph`'s independently-developed `specificity_weights` (`1/log(1+n_sharing_name)`) is the same idea — IDF-style suppression of common names — arrived at separately.

7. **Caveats on transfer.** HotpotQA and 2Wiki are Wikipedia multi-hop QA; the entity distribution is nothing like drug/gene/condition vocabulary, and SPRIG's graph uses generic `en_core_web_sm` NER — which CTRA's own evaluation (`docs/ner-evaluation-guide.md`) found markedly inferior to GLiNER for biomedical retrieval. A biomedical graph with good NER might fare better than SPRIG's does here. These numbers justify **ordering the work hybrid-first**; they do not settle the question for CTRA. Only a CTRA-specific retrieval benchmark (TREC-CT 2021) can.

8. **Methodological template.** The ablation discipline — one variable isolated per run, paired bootstrap CIs, a robustness check removing the tuning subset, explicit peak-RSS reporting — is a good model for the retrieval eval harness CTRA is missing (`research/rag-alternatives-hybrid-retrieval.md` § 8).

## Provenance of the Graph Variants

`GraphHybrid`, `GraphDense` and `GraphRRF` are **names coined in this paper**, not references to prior work. They are one algorithm — PPR over the entity–document graph — differing only in where the seed distribution comes from. SPRIG's 28 references contain no entry for any of the three names, and no external work uses them.

Their constituent methods do have sources, now vendored alongside this paper:

| Variant | Seed source | Source paper |
|---|---|---|
| `Graph` | query entities | — (this paper) |
| `GraphHybrid` | top-*k* BM25 passages | [Okapi at TREC-3](robertson-trec3-1994-okapi-bm25.md) — Robertson et al. 1994 (BM25) |
| `GraphDense` | top-*k* dense passages | [C-Pack](2309.07597v5.md) — Xiao et al. 2024 (`bge-small-en-v1.5`) |
| `GraphRRF` | top-*k* of the RRF-fused list | [Reciprocal Rank Fusion](cormack-sigir2009-rrf.md) — Cormack et al. 2009 |

**SPRIG uses RRF with *k* = 60 but does not cite Cormack et al.** That constant traces to a single pilot investigation in the 2009 paper and was never re-tuned; see the sweep reproduced in [cormack-sigir2009-rrf.md](cormack-sigir2009-rrf.md).

The seeded-PPR architecture itself also predates this paper:

- [HippoRAG](2405.14831v3.md) (NeurIPS 2024) — established entity-graph + PPR retrieval; seeds from query entities, like SPRIG's plain `Graph`.
- [LightPAL](2406.12494v2.md) (2024) — seeds PPR from a conventional sparse or dense retriever, the same architecture as `GraphHybrid`/`GraphDense`, two years earlier.
- [MixPR](2412.06078v1.md) (2024) — SPRIG's "TF–IDF Graph PPR (MixPR-like)" baseline. Note SPRIG miscites its title; see that document.

One caution when reading the damping factor here: SPRIG uses α = 0.15, HippoRAG 0.5, MixPR 0.6, LightPAL 0.8 teleport. Four papers, four values, each reported as tuned — this parameter does not transfer.
