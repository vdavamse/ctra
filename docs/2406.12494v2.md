## Abstract

Open-Domain Multi-Document Summarization (ODMDS) is the task of generating summaries from large document collections in response to user queries. Traditional retrieve-then-summarize approaches fall short for open-ended queries in ODMDS tasks. These queries often require broader context than initially retrieved passages provide, making it challenging to retrieve all relevant information in a single search. While iterative retrieval methods have been explored for multi-hop question answering (MQA), it's impractical for ODMDS due to high latency from repeated LLM inference. Accordingly, we propose LightPAL, a lightweight passage retrieval method for ODMDS. LightPAL leverages an LLM to pre-construct a graph representing passage relationships, then employs random walk during retrieval, avoiding iterative LLM inference. Experiments demonstrate that LightPAL outperforms naive sparse and pre-trained dense retrievers in both retrieval and summarization metrics, while achieving higher efficiency compared to iterative MQA approaches.

## Problem Statement

For open-ended queries ("summarize what was decided about the budget"), the passages that are *directly similar to the query* are not the full set of passages needed. A passage extracted from a larger document may not be self-explanatory; it needs surrounding context to be understood, and even a self-contained passage benefits from related text.

Naive retrieval scores only query–passage relevance and therefore cannot capture these relationships. Iterative retrieval can, but at the cost of repeated LLM inference inside the query's latency budget — the paper measures a competing method (PromptRank) at **over 10 seconds per query**, which it describes as "prohibitively slow for interactive RAG systems."

**The core move: shift the LLM from query time to index time.**

## Key Contributions

1. **LightPAL** — a two-phase method that builds a passage-relationship graph offline with an LLM and traverses it online with PPR, so no LLM runs at query time.
2. **A graph-construction signal based on conditional generation probability** — `P_LM(d_j | d_i)` — rather than on entity extraction or embedding similarity.
3. **A candidate-pruning scheme** that makes an otherwise O(n²) construction tractable.
4. **Measured evidence that small LLMs suffice**: Qwen2.5-0.5B already captures most of the gain.
5. **Latency measurements** showing PPR retrieval is ~1,000× faster than query-time LLM reranking.

## Methodology / Architecture

### Phase 1 — Passage graph construction (offline)

For each ordered pair of passages, the **context score** is the LLM's conditional probability of generating *d_j* given *d_i* as context:

```
ContextScore(d_i, d_j) = P_LM(d_j | d_i)
```

The rationale: conditional generation probability "can richly determine the relevance between passages by considering the diverse styles and domains" and captures "the fluency of the passage sequence," which reconstructs relationships between passages that were originally part of a cohesive document *and* builds new ones between passages from different documents.

**Tractability.** Scoring all pairs is prohibitive, so construction is two-stage:
1. Retrieve the **top-k′ = 100** most similar candidate passages for each passage with a lightweight embedding model (`bge-large-en-v1.5` — see [2309.07597v5](2309.07597v5.md)).
2. Run the LLM only on those candidates, keeping edges to the **top-k = 5** by context score.

So the LLM is invoked 100× per passage, not n× per passage — but this is still **100 LLM forward passes per passage** at index time.

### Phase 2 — Retrieval (online)

1. **Initial passage retrieval**: retrieve **D_init** with any sparse or dense retriever (BM25 or `bge-large-en-v1.5` in the experiments).
2. **Context passage retrieval**: run **PPR** on the pre-built graph, seeded from D_init, to obtain **D_context**.
3. Return **D_q = D_init ∪ D_context**.

**Settings**: |D_init| = top **60%** of K; PPR jumps uniformly to the top-20 of D_init with probability 1 − α, where **α = 0.2**; edge weights uniform.

> Note the α convention is the opposite of MixPR's: here 1 − α is the teleport probability, so α = 0.2 means **80% teleport mass**. This is a very heavily seed-anchored walk — consistent with the task, where the initial retrieval is trusted and PPR only fills in context.

### Comparison to the other seeded-PPR papers in `docs/`

| | Graph built from | Seeded from | Index-time cost |
|---|---|---|---|
| **HippoRAG** ([2405.14831v3](2405.14831v3.md)) | LLM OpenIE triples + synonymy | query entities | 1 LLM call / passage |
| **MixPR** ([2412.06078v1](2412.06078v1.md)) | TF-IDF chunk proximity | last chunk (= query) | none |
| **LightPAL** (this) | LLM `P(d_j\|d_i)` over 100 candidates | **conventional retriever output** | ~100 LLM passes / passage |
| **SPRIG GraphHybrid/Dense/RRF** ([2602.23372v1](2602.23372v1.md)) | NER co-occurrence | **BM25 / dense / RRF top-k** | NER only |

LightPAL and SPRIG share the seeding architecture; they differ entirely in how the graph is built.

## Results

### Retrieval (Table 2, Precision@k / Recall@k)

| Method | Story P@k | Story R@k | Meeting P@k | Meeting R@k | RAG-QA P@k | RAG-QA R@k |
|---|---|---|---|---|---|---|
| `bge-large-en-v1.5` | 31.15 | 36.27 | 10.34 | 12.79 | **64.25** | **71.49** |
| + LightPAL (Qwen 0.5B) | 37.16 | 42.73 | 11.37 | 14.26 | 62.78 | 70.58 |
| + LightPAL (Qwen 1.5B) | 38.50 | 44.24 | 11.41 | 14.32 | 63.14 | 70.73 |
| + LightPAL (Qwen 3B) | **39.55** | **45.30** | **11.47** | **14.38** | 63.43 | 70.84 |
| BM25 | — | — | — | — | — | — |
| + LightPAL (Qwen 0.5B) | 48.75 | 55.05 | 12.30 | 15.17 | 54.58 | 60.90 |
| + LightPAL (Qwen 1.5B) | 49.72 | 55.94 | 12.18 | 15.13 | 54.95 | 61.42 |

**Honest reading**: LightPAL improves most dataset/retriever combinations — up to +9 points on Story — **but it makes RAG-QA with `bge-large` slightly worse** (71.49 → 70.58–70.84). The authors state this exception explicitly. RAG-QA is the dataset with the highest baseline (71.49) and the lowest relevant-passage ratio (0.3%); where the dense retriever already finds what is needed, graph expansion adds noise.

LightPAL also outperforms PromptRank by 3–6% on Story and RAG-QA.

### Model size

Larger LLMs improve retrieval "gradually," especially Recall@k — but "performance gains from larger models are relatively small compared to improvements over baseline models. **This suggests that even models smaller than 0.5B may still offer substantial benefits.**"

### Latency (Table 3, ms per query)

| Dataset | PromptRank | **LightPAL (Context PR)** |
|---|---|---|
| Story | 7.57 × 10⁴ | **6.02** |
| Meeting | 3.09 × 10⁴ | **113.31** |
| RAG-QA | 1.96 × 10⁴ | **23.09** |

**~1,000× faster.** LightPAL's context retrieval adds only 10–20× the initial search cost, which the authors argue "is unlikely to impair the real-time performance of RAG systems." PPR cost is linear in the number of edges.

Hardware: `bge-large-en-v1.5` query embedding on NVIDIA L40; search for bge, BM25 and LightPAL on **a single thread** of an AMD EPYC 9554; PromptRank's Qwen2.5-3B inference on an NVIDIA L40S.

## Limitations

- **Index-time cost is the hidden price, and the paper does not report it.** ~100 LLM forward passes per passage, with no wall-clock or dollar figure given anywhere. The "lightweight" claim is about *query* time only. At CTRA's scale this is the decisive omission.
- **Small corpora.** 1,190–13,074 passages. Graph construction is O(n · k′) LLM calls, so the approach's behaviour at 10⁶+ passages is untested.
- **It does not always help.** RAG-QA + `bge-large` degrades. No analysis is offered of when graph expansion hurts.
- **Authors' stated limitations (§7)**: only two summarizer LLMs were evaluated (Llama-3.1-8B-Instruct, MegaBeam-Mistral-7B-512), and comparison against other iterative reasoning methods is limited.
- **Uniform edge weights.** The context scores rank candidates but are discarded when building the graph — PPR treats all 5 retained edges identically.
- **Narrow task framing.** ODMDS, not general retrieval; the "context passages" objective is specific to summarization.

## Relevance to CTRA

1. **It is the architectural precedent for seeding PPR from a conventional retriever** — the pattern `research/linearrag-improvements.md` item 6 proposes for CTRA. LightPAL validated it in 2024; SPRIG later named the variants and measured that the RRF-seeded version is strongest. Two independent groups converging on seed-side integration is a stronger prior than either paper alone.

2. **The negative result is the most useful part.** LightPAL *hurts* on RAG-QA with a strong dense retriever — the dataset with the highest baseline and sparsest relevance. The lesson for CTRA: **graph expansion is not free, and it pays off least where the base retriever is already strong.** This argues directly for the sequencing already in `research/rag-alternatives-hybrid-retrieval.md` — build and measure the hybrid retriever first, add PPR only if measurement shows a gap. The graph is a fix for a deficit, not an unconditional upgrade.

3. **The index-time silence is a warning to read other "lightweight" claims carefully.** LightPAL's query-time story is excellent (6–113 ms) and its index-time story is absent. CTRA has already been bitten by exactly this asymmetry: LinearRAG's published efficiency figures did not surface that GLiNER indexing runs at **1.13 doc/s → 22.8 days for ClinicalTrials.gov alone** on this hardware. When evaluating any retrieval paper for CTRA, the question to ask first is what it costs to *build*, not what it costs to *query*.

4. **"Even models smaller than 0.5B may still offer substantial benefits"** matches CTRA's own measured GLiNER result — `uni-small` at 5.63× production throughput, `uni-base` at 3.50× (`research/linearrag-improvements.md`, item 10). Two independent settings where the small model captures most of the value. Neither is proof for CTRA's corpus, but together they justify running the F1 comparison before assuming the large model is required.

5. **The 80%-teleport setting is a useful data point on the α disagreement.** LightPAL anchors PPR very heavily to the seed set (1 − α = 0.8), consistent with treating PPR as a *context-filling* step rather than a retriever. Against HippoRAG's 0.5, SPRIG's 0.15 and MixPR's 0.6, the spread across four papers is wide enough that CTRA must measure this locally rather than inherit a value.

6. **Not directly adoptable.** The `P_LM(d_j | d_i)` graph requires ~100 LLM passes per passage. On CTRA's corpus and hardware this is strictly worse than the GLiNER wall already documented. The *seeding architecture* transfers; the *graph construction* does not.

## Code / Data Availability

No public code repository is linked in the paper. Components are standard: `bge-large-en-v1.5` for candidate retrieval, Qwen2.5 (0.5B/1.5B/3B) for context scoring, and any PPR implementation (NetworkX, SciPy). The ODSum datasets (Story, Meeting) are available at https://github.com/yale-nlp/ODSum.
