## Abstract

Retrieval-Augmented Generation (RAG) is widely used to mitigate hallucinations of Large Language Models (LLMs) by leveraging external knowledge. While effective for simple queries, traditional RAG systems struggle with large-scale, unstructured corpora where information is fragmented. Recent advances incorporate knowledge graphs to capture relational structures, enabling more comprehensive retrieval for complex, multi-hop reasoning tasks. However, existing graph-based RAG (GraphRAG) methods rely on unstable and costly relation extraction for graph construction, often producing noisy graphs with incorrect or inconsistent relations that degrade retrieval quality.

The paper proposes **Linear Graph-based Retrieval-Augmented Generation (LinearRAG)**, an efficient framework that enables reliable graph construction and precise passage retrieval. LinearRAG constructs a relation-free hierarchical graph, termed **Tri-Graph**, using only lightweight entity extraction and semantic linking, avoiding unstable relation modeling. This new paradigm scales linearly with corpus size and incurs no extra LLM token consumption. For retrieval, LinearRAG adopts a two-stage strategy: (i) relevant entity activation via local semantic bridging, followed by (ii) passage retrieval through global importance aggregation. Extensive experiments on four datasets demonstrate that LinearRAG significantly outperforms baseline models.

## Problem Statement

Existing GraphRAG systems suffer from two critical deficiencies rooted in their dependence on explicit relation extraction for knowledge graph construction:

1. **Local Inaccuracy**: Relation extraction models frequently produce factually incorrect triples. For example, the sentence "Einstein did not win the Nobel Prize for his theory of relativity" may be misrepresented as the triple *(Einstein, won Nobel Prize for, theory of relativity)*, fundamentally altering factual meaning.

2. **Global Inconsistency**: Relation extraction is performed locally on individual text passages with no mechanism to validate or reconcile connections across the entire corpus, leading to redundant or contradictory relations and structurally fragmented graphs with poor connectivity.

These deficiencies cause GraphRAG methods to frequently underperform even naive RAG approaches on real-world tasks. While graph-based retrieval increases recall, it concurrently introduces substantial noise and ambiguity into retrieved contexts. Preliminary experiments on GraphRAG-Bench showed that GraphRAG methods like LightRAG and HippoRAG achieve only 36.86%--54.61% context relevance, compared to 62.87% for vanilla RAG.

## Key Contributions

1. **Identification of GraphRAG limitations**: The authors systematically diagnose how reliance on unstable relation extraction introduces noise and structural inconsistencies, motivating the design of LinearRAG as a framework that enables reliable graph construction and precise passage retrieval while maintaining linear scalability.

2. **Relation-free hierarchical graph (Tri-Graph)**: LinearRAG constructs a relation-free hierarchical graph using only lightweight entity extraction (via spaCy NER) and semantic linking, avoiding the instability of traditional relation modeling and **reducing indexing time by over 77%** with **zero LLM token consumption** during indexing and retrieval.

3. **Two-stage retrieval mechanism**: A retrieval strategy combining local semantic bridging for precise entity activation with global importance aggregation (via Personalized PageRank) for passage recall, enabling accurate, noise-resilient, single-pass multi-hop retrieval.

4. **State-of-the-art results**: Extensive experiments on four benchmark datasets demonstrate that LinearRAG consistently outperforms all state-of-the-art baselines in retrieval quality, generation accuracy, and scalability.

## Methodology / Architecture

### Overview

LinearRAG introduces a new GraphRAG paradigm with two phases: **Offline Construction** and **Online Retrieval**.

### Phase I: Token-Free Graph Construction (Offline)

LinearRAG constructs a hierarchical **Tri-Graph** with three types of nodes at multiple granularities:

- **Entity nodes (V_e)**: Named entities extracted via lightweight NER models (spaCy with BERT-based models)
- **Sentence nodes (V_s)**: Sentences obtained by segmenting passages using punctuation
- **Passage nodes (V_p)**: Original text passages from the corpus

**Edges** are defined by two sparse adjacency matrices:

- **Contain matrix C** (|V_p| x |V_e|): Binary matrix where C_ij = 1 if passage p_i contains entity e_j
- **Mention matrix M** (|V_s| x |V_e|): Binary matrix where M_ij = 1 if sentence s_i mentions entity e_j

Key design properties:
- **Linear scalability**: When new passages arrive, only those passages undergo sentence segmentation, NER, and edge construction
- **Zero token cost**: NER is performed using lightweight language models (spaCy) without incurring LLM API costs
- **Sparse storage**: Matrices C and M exploit intrinsic sparsity (~4 entities per sentence, ~10 per passage) for efficient memory usage
- **Information-lossless**: By retaining original passages as knowledge carriers, all contextual information is preserved

### Phase II: Two-Stage Passage Retrieval (Online)

#### Stage 1: Relevant Entity Activation via Semantic Bridging

This stage operates on the **entity-sentence subgraph** (passage nodes are fixed) to identify intermediate entities that bridge multi-hop relations:

1. **Initial entity activation**: Extract entities from query q using spaCy. For each extracted entity, find the most similar entity in the knowledge graph. Set initial activation score to the similarity score:
   - a_q = [a_{q,i}], where a_{q,i} = indicator * sim(e_q, e_i)

2. **Query-sentence relevance distribution**: Compute contextual association between query q and each sentence s_i as a similarity vector sigma_q.

3. **Semantic propagation**: Iteratively propagate similarities through the sentence-entity bipartite graph to activate relevant intermediate entities:
   - a^t_q = MAX(M^T(sigma_q * (M * a^{t-1}_q)), a^{t-1}_q)
   - This enables n-hop entity activation within only n iterations (n <= 4)
   - Each iteration involves three matrix multiplications and one MAX operation
   - Sparse matrix multiplication (SpMM) is used for efficiency

4. **Dynamic pruning**: At each propagation step, a threshold delta prunes entities whose relevance score falls below delta. Propagation terminates automatically when no new entity surpasses the threshold, constraining expansion to high-quality semantic paths.

#### Stage 2: Passage Retrieval via Global Importance Aggregation

This stage operates on the **entity-passage subgraph** (sentence nodes are fixed) using activated entities from Stage 1:

1. **Personalized PageRank (PPR)**: Computes refined global importance scores for each node:
   - I(v_i) = (1 - d) + d * sum_{v_j in B(v_i)} I(v_j) / deg(v_j)
   - Damping factor d = 0.85

2. **Hybrid initialization for passage nodes**: Passage node importance combines DPR-based similarity and entity-level information:
   - I(v | v in V_p) = (lambda * sim(q, v) + ln(1 + sum_{e_i in E_a} a^(i)_q * ln(1 + N_{e_i}) / L_{e_i})) * W_p
   - Where N_{e_i} is entity occurrence count, L_{e_i} is hierarchical level, lambda is a trade-off coefficient

3. **Top-k selection**: Passages ranked by PPR scores; top-k (k=5) highest-scoring passages are retrieved.

### Embedding Model

All experiments use **all-mpnet-base-v2** as the sentence embedding model. The framework is robust to embedding model choice (tested with all-MiniLM-L6-v2, bge-large-en-v1.5, e5-large-v2 with modest variation).

### Generation

All RAG approaches use **GPT-4o-mini** for both generation and evaluation tasks.

### Ablation Study

Both core modules are critical:
- **Without Entity Activation**: Performance drops across all datasets (e.g., 66.95% to 64.40% on 2Wiki)
- **Without Global Importance Aggregation**: Performance drops comparably (e.g., 66.95% to 64.20% on 2Wiki)
- The two stages serve complementary purposes: Stage 1 uncovers hidden logical relationships; Stage 2 evaluates document importance from a global perspective

### Key Hyperparameters

- **Threshold delta**: Controls dynamic pruning; optimal value delta = 4. Too small introduces noise; too large limits entity coverage.
- **Trade-off coefficient lambda**: Controls balance between DPR-based passage similarity and entity-level information; optimal at small values (e.g., 0.05), indicating entity information is the primary component.

## Limitations

The authors do not include an explicit limitations section, but the following can be inferred from the paper:

1. **NER quality dependency**: The framework relies on spaCy for named entity recognition; NER errors (missed or incorrect entities) will propagate through the Tri-Graph and affect retrieval quality, particularly in specialized domains where off-the-shelf NER models may underperform.

2. **Entity-centric assumption**: The framework assumes that entities serve as the primary anchors connecting information across passages. This may not hold for all query types, particularly those involving abstract concepts, procedural reasoning, or relationships that are not entity-mediated.

3. **Evaluation scope**: Experiments are limited to English-language datasets and a relatively narrow set of multi-hop QA benchmarks. Generalization to other languages, document types (e.g., tables, structured data), or task types (e.g., summarization, dialogue) is not demonstrated.

4. **Embedding model ceiling**: While LinearRAG is robust across embedding models, its retrieval quality is still bounded by the semantic representation quality of the underlying sentence embeddings.

5. **Static graph**: The Tri-Graph is constructed offline; dynamic corpus updates require incremental re-indexing (though this is stated to be linear-time).

## Relevance to CTRA

The CTRA (Clinical trial outcome prediction using multimodal data from ClinicalTrials.gov) project can benefit from LinearRAG in several ways:

1. **Replacing pgvector in AutoCT's RAG pipeline**: LinearRAG's Tri-Graph approach could replace the current pgvector-based vector similarity search in AutoCT's RAG pipeline. Instead of flat embedding-based retrieval, LinearRAG would enable multi-hop retrieval across trial data -- critical for clinical trial outcome prediction where relevant information (e.g., drug mechanisms, patient populations, endpoint definitions, historical trial outcomes) is distributed across many separate trial records and documents.

2. **Multi-hop reasoning over clinical trial data**: Clinical trial outcome prediction inherently requires multi-hop reasoning -- connecting drug properties to mechanism of action, to patient population characteristics, to historical outcomes of similar trials. LinearRAG's semantic bridging can discover these implicit entity chains (e.g., Drug -> Indication -> Biomarker -> Endpoint -> Historical Outcome) without requiring expensive relation extraction over clinical text.

3. **Cost efficiency for large-scale ClinicalTrials.gov data**: ClinicalTrials.gov contains 400,000+ trial records. LinearRAG's zero-token indexing and linear scalability make it practical for indexing this entire corpus without incurring prohibitive LLM API costs, unlike GraphRAG methods that require LLM-based relation extraction.

4. **Domain-specific NER compatibility**: LinearRAG uses spaCy for NER, which can be swapped with domain-specific biomedical NER models (e.g., SciSpaCy, BioBERT-based NER) to accurately extract clinical entities such as drug names, diseases, biomarkers, and endpoints from trial descriptions.

5. **Medical domain validation**: The paper already demonstrates LinearRAG's effectiveness on a Medical dataset from GraphRAG-Bench (sourced from NCCN clinical guidelines), achieving 63.72% GPT-Acc. versus 60.77% for HippoRAG2 and 61.68% for vanilla RAG. This directly validates its applicability to clinical/medical text retrieval.

6. **Noise resilience**: Clinical trial data from ClinicalTrials.gov is heterogeneous and often contains inconsistent terminology. LinearRAG's relation-free approach avoids the noise amplification problem that relation extraction would introduce on such data.
