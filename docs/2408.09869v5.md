## Abstract

This technical report introduces Docling, an easy to use, self-contained, MIT-licensed open-source package for PDF document conversion. It is powered by state-of-the-art specialized AI models for layout analysis (DocLayNet) and table structure recognition (TableFormer), and runs efficiently on commodity hardware in a small resource budget. The code interface allows for easy extensibility and addition of new features and models.

## Problem Statement

Converting PDF documents back into a machine-processable format has been a major challenge for decades due to huge variability in formats, weak standardization, and printing-optimized characteristics that discard most structural features and metadata. With the advent of LLMs and application patterns such as retrieval-augmented generation (RAG), leveraging rich content in PDFs has become critical. Most existing solutions are commercial or cloud-based, and the few open-source tools leave a significant feature and quality gap compared to proprietary solutions.

## Key Contributions

1. Released **Docling**, an MIT-licensed, self-contained Python package for high-quality PDF-to-JSON/Markdown conversion that runs entirely locally on commodity hardware.
2. Open-sourced two specialized AI models:
   - **Layout analysis model** based on RT-DETR, retrained on DocLayNet (a large human-annotated dataset for document-layout analysis)
   - **TableFormer** -- a state-of-the-art vision-transformer model for table structure recognition
3. Developed a custom PDF parser (**docling-parse**) based on the low-level qpdf library, addressing licensing and quality issues with existing PDF parsing libraries.
4. Provided a linear, extensible processing pipeline with customizable model chains.
5. Demonstrated efficient performance: 1.27--2.45 pages/second on commodity hardware (Apple M3 Max and Intel Xeon), with peak memory of 2.42--6.20 GB.
6. Integrated with downstream tools: quackling (for RAG with LlamaIndex), IBM Data Prep Kit (for scalable dataset construction).

## Methodology/Architecture

**Processing pipeline (linear, sequential):**

1. **PDF Backend** -- Parses PDF pages to extract:
   - Programmatic text tokens (string content + coordinates)
   - Bitmap images of each page
   - Two backend options: docling-parse (default, custom-built on qpdf) and pypdfium (faster, lower quality)

2. **Model Pipeline** (per-page, independently applied):
   - **OCR** (optional) -- Uses EasyOCR; feeds 216 dpi page images; supports 80+ languages; ~30s/page on CPU
   - **Layout Analysis** -- RT-DETR-based object detector retrained on DocLayNet; processes 72 dpi images; sub-second latency on CPU; predicts bounding boxes for: paragraphs, section titles, list items, captions, figures, tables, etc. Post-processing removes overlapping proposals and intersects with PDF text tokens.
   - **Table Structure Recognition** -- TableFormer (vision-transformer); predicts logical row/column structure, column headers, row headers, body cells; handles borderless tables, empty cells, spans, hierarchies; 2--6 seconds per table on CPU. Predictions matched back to PDF cells to avoid re-transcription.

3. **Assembly and Post-Processing:**
   - Aggregates per-page results into a unified document object (defined in docling-core)
   - Document language detection
   - Reading order correction
   - Figure-caption matching
   - Metadata labeling (title, authors, references)
   - Serialization to JSON or Markdown

**Key architectural decisions:**
- All models run locally (no cloud dependency)
- Inference uses onnxruntime (layout model) and PyTorch (TableFormer)
- Model weights hosted on HuggingFace (ds4sd/docling-models)
- Extensible via BaseModelPipeline subclassing -- models implement Python Callable interface

## Datasets

**Models are trained on:**
- **DocLayNet** -- A large human-annotated dataset for document-layout analysis with 80,863 manually annotated pages from diverse sources (financial reports, manuals, scientific articles, laws, patents, government tenders). 11 distinct layout classes: Caption, Footnote, Formula, List-item, Page-footer, Page-header, Picture, Section-header, Table, Text, Title. Published in COCO format.
- Additional proprietary datasets (not specified)

**Test set for benchmarking:**
- 3 arXiv papers + 2 IBM Redbooks = 225 pages total

## Results

**Performance benchmarks (225-page test set, OCR disabled):**

| CPU | Thread Budget | Backend | Time-to-Solution | Pages/sec | Peak Memory |
|-----|-------------|---------|------------------|-----------|-------------|
| Apple M3 Max (16 cores) | 4 | native (docling-parse) | 177 s | 1.27 | 6.20 GB |
| Apple M3 Max (16 cores) | 16 | native | 167 s | 1.34 | 6.20 GB |
| Apple M3 Max (16 cores) | 4 | pypdfium | 103 s | 2.18 | 2.56 GB |
| Apple M3 Max (16 cores) | 16 | pypdfium | 92 s | 2.45 | 2.56 GB |
| Intel Xeon E5-2690 (16 cores) | 4 | native | 375 s | 0.60 | 6.16 GB |
| Intel Xeon E5-2690 (16 cores) | 16 | native | 244 s | 0.92 | 6.16 GB |
| Intel Xeon E5-2690 (16 cores) | 4 | pypdfium | 239 s | 0.94 | 2.42 GB |
| Intel Xeon E5-2690 (16 cores) | 16 | pypdfium | 143 s | 1.57 | 2.42 GB |

**Quality highlights (demonstrated in appendix):**
- Accurate layout segmentation for complex multi-column documents
- Correct reading order recovery
- Table structure recognition preserving spanning cells, headers, and hierarchies
- Metadata extraction (title, authors, references)
- Page headers/footers suppressed in Markdown output for uninterrupted content

**DocLayNet model performance (from referenced paper):**
- YOLOv5x6 achieves best mAP@0.5-0.95 of 76.8% overall on DocLayNet test set
- Human inter-annotator agreement: 82--83% mAP
- Gap of ~6--10% between models and human annotators

## Limitations

- **OCR speed:** EasyOCR runs ~30 seconds/page on CPU, which is slow. The team is seeking community collaboration for faster OCR backends.
- **GPU acceleration:** Largely untested at time of report, work-in-progress.
- **pypdfium backend** offers faster and lower-memory processing but with worse quality, especially for table structure recovery.
- **Text in figures** is currently dropped (only captions are retained).
- **Column-wrapping paragraphs** may be broken into separate segments when they span across columns.
- **Font encoding issues** may occur with certain PDFs in the default backend.
- The report covers version 1.0; future models (figure classifier, equation recognizer, code recognizer) are planned but not yet available.

## Relevance to CTRA

Docling is relevant to the CTRA project as a **practical tool** rather than a scientific methodology peer:

1. **PDF protocol parsing:** CTRA may need to process clinical trial protocol documents that are in PDF format (e.g., full protocol documents not available as structured data on ClinicalTrials.gov). Docling provides high-quality conversion of these PDFs to structured JSON/Markdown.
2. **Table extraction from protocols:** Clinical trial protocols often contain tables with eligibility criteria, endpoint definitions, visit schedules, and study design parameters. Docling's TableFormer can accurately extract these structured tables, which could feed into CTRA's feature engineering pipeline.
3. **Literature processing:** For systematic review of clinical trial risk literature (such as the papers being summarized here), Docling can efficiently convert research PDFs into machine-processable text.
4. **Layout-aware extraction:** Docling's ability to distinguish section headers, captions, footnotes, and body text enables more intelligent extraction of specific protocol sections relevant to uninformativeness prediction.
5. **Local, efficient processing:** Running entirely locally with MIT license makes it suitable for processing potentially sensitive clinical trial documents without cloud dependencies.
6. **Integration with RAG pipelines:** Through quackling and LlamaIndex integration, Docling can support knowledge retrieval from large collections of clinical trial documents, which could augment CTRA's analysis.
7. **Scalable dataset construction:** Integration with IBM Data Prep Kit enables building large-scale training datasets from PDF protocol collections.
